## Architectural Themes

Across the collection, several ideas appear repeatedly.

### Make intent explicit

The project consistently favors explicit user intent over implicit behavior,
hidden discovery, or inferred configuration.

### Prefer composition

New capabilities should compose with existing architectural concepts rather than
introducing special cases or redefining established behavior.

### Keep concepts small

The project intentionally favors a small manifest language, a focused engine, and
narrowly scoped responsibilities.

### Treat public interfaces as contracts

Externally visible behavior evolves deliberately and conservatively.

### Optimize for understanding

The project values inspectability, documentation, diagnostics, and predictable
behavior because software that is easier to understand is easier to trust.

## Using These ADRs

These documents are intended for several audiences.  Users can understand what
guarantees the project makes and why particular behaviors exist.  Contributors
should consult relevant ADRs before proposing architectural changes.  Writers may
use the records as source material for articles, presentations, or long-form
writing about software architecture, engineering culture, and system design.

Automated tools should treat individual ADRs as atomic architectural decisions.
The generated list above is navigation, not a substitute for reading the source
records or `doc/decisions.md` when broader decision context is needed.

## Writing Future ADRs

When deciding whether something deserves an ADR, ask whether it materially
affects long-term architecture, whether future contributors would reasonably ask
why the decision was made, and whether losing the rationale would make the
project harder to understand.

If the decision primarily concerns implementation style, coding conventions,
repository organization, or day-to-day workflow, contributor documentation is
usually a better home.

## Relationship to Other Documentation

The ADRs are the canonical record of architectural decisions.  Other documents,
including the project README, contributor guides, examples, current threat model,
and architecture overviews, should summarize, organize, and reference these
decisions rather than duplicate or replace them.

The repository's current STRIDE threat model remains maintained separately in
`doc/threat_model.md`.  Its Mermaid diagrams are not generated by this ADR index
and are not replaced by this reference-documentation workflow.

## Closing Thought

Good architecture is more than a collection of correct technical decisions.  It
is a collection of decisions that remain understandable long after the
implementation has changed.  That is the purpose of this directory.
